Why Background Jobs Exist??

In a naive implementation, everything happens inside the request-response cycle:
Client sends request
      ↓
Server does the work (sends email, generates report, calls 3rd party)
      ↓
Server sends response

This is wrong for anything that takes time. The client is blocked waiting. If the task takes 10 seconds, the client hangs for 10 seconds. If the task fails halfway, the whole request fails. If you get 1000 requests at once, 1000 tasks run simultaneously and your server dies.
The fix is to decouple work from the request. The API responds immediately with "job accepted" and hands the actual work off to a background worker.

Client sends request
      ↓
Server enqueues job → responds with 202 Accepted immediately
      ↓
Background worker picks up job and does the actual work

The client gets a fast response. The work happens reliably in the background. The system can scale workers independently from the API.




Core Concepts


Queues
A queue is a data structure where producers push jobs in and consumers (workers) pull jobs out, typically in FIFO order. Redis (with BullMQ) and RabbitMQ are the most common queue backends in Node.js.
Producer (API Server)          Queue          Consumer (Worker)
       |                         |                    |
       |  -- add job ----------> |                    |
       |                         | -- pick job -----> |
       |                         |                    | (does the work)
       |                         | <-- mark done ---- |
A job sits in the queue until a worker is free to process it. If you have 10 workers, 10 jobs run in parallel. You can scale workers up or down independently of your API.




Idempotency

This is one of the most important concepts in distributed systems and comes up constantly in interviews.
An operation is idempotent if running it multiple times produces the same result as running it once.
Why does this matter for background jobs? Because networks are unreliable. A worker might process a job, succeed, but crash before it can mark the job as done in the queue. The queue retries the job. Now the operation runs twice.
If your job sends a welcome email, the user gets two emails. That's bad. If your job charges a payment, the user gets charged twice. That's very bad.
Making jobs idempotent:

js// Bad — not idempotent
async function sendWelcomeEmail(userId) {
  await emailService.send(user.email, "Welcome!");
}

// Good — idempotent
async function sendWelcomeEmail(userId) {
  const alreadySent = await db.query(
    "SELECT 1 FROM email_log WHERE user_id = ? AND type = 'welcome'",
    [userId]
  );
  if (alreadySent) return; // already done, safe to exit

  await emailService.send(user.email, "Welcome!");

  await db.query(
    "INSERT INTO email_log (user_id, type) VALUES (?, 'welcome')",
    [userId]
  );
}
Check before acting. Log after acting. If the job runs twice, the second run is a no-op.
For payments, use idempotency keys — a unique token per transaction that the payment provider (Stripe, Razorpay) uses to detect and reject duplicate requests.

Retry Strategies


Jobs fail. Third-party APIs go down, DB connections drop, network hiccups happen. You need a strategy for what to do when a job fails.
Immediate retry — retry right away. Useless if the failure is transient (the API is still down 100ms later).
Fixed delay retry — wait a fixed time between retries (e.g., retry after 5s every time). Better, but still hammers a downed service.
Exponential backoff — double the wait time on each failure. The standard approach.
Attempt 1 fails → wait 1s
Attempt 2 fails → wait 2s
Attempt 3 fails → wait 4s
Attempt 4 fails → wait 8s
Attempt 5 fails → move to dead letter queue


Exponential backoff with jitter — add random variance to the wait time. Without jitter, all failed jobs from a burst retry simultaneously and cause another burst.
js// BullMQ config
const queue = new Queue("emails", {
  defaultJobOptions: {
    attempts: 5,
    backoff: {
      type: "exponential",
      delay: 1000, // starts at 1s, doubles each attempt
    },
  },
});

Dead Letter Queues (DLQ)
When a job exhausts all its retries, it needs to go somewhere — you can't just silently drop it. A Dead Letter Queue is a separate queue where permanently failed jobs land.
Main Queue → Worker fails repeatedly → DLQ
The DLQ lets you:

Alert engineers that something is broken
Inspect failed jobs and understand why
Replay jobs manually after fixing the root cause

In production you monitor the DLQ size. A spike in DLQ depth means something is systematically broken.
js// BullMQ — jobs that exhaust retries go to "failed" state
// You can then move them to a separate DLQ queue or process them

worker.on("failed", async (job, err) => {
  if (job.attemptsMade === job.opts.attempts) {
    await dlqQueue.add("dead", { originalJob: job.data, error: err.message });
    await alerting.notify(`Job ${job.name} permanently failed: ${err.message}`);
  }
});

Use Cases
Email Sending
The most common example. Never send emails synchronously in a request handler.
js// ❌ Rookie mistake — blocks the response
app.post("/register", async (req, res) => {
  await db.createUser(req.body);
  await emailService.sendWelcome(req.body.email); // what if this takes 3s? what if it fails?
  res.json({ success: true });
});

// ✅ Correct — enqueue and respond immediately
app.post("/register", async (req, res) => {
  const user = await db.createUser(req.body);
  await emailQueue.add("welcome", { userId: user.id, email: user.email });
  res.status(202).json({ success: true }); // 202 Accepted = request received, work ongoing
});

// Worker runs separately
const worker = new Worker("emails", async (job) => {
  await emailService.sendWelcome(job.data.email);
});
If the email service is down, the job retries automatically. Your API stays fast. Email delivery is decoupled from signup success.

Notifications
Push notifications, in-app notifications, and SMS follow the same pattern. The trigger (a comment, a like, a payment) happens in the request. Notification dispatch happens in the background.
One job might fan out into many notifications:
js// API: someone posts a comment
await notifQueue.add("comment", {
  postId: post.id,
  commenterId: user.id,
  postOwnerId: post.authorId,
});

// Worker: figure out who to notify and dispatch
async function processCommentNotif(job) {
  const { postId, commenterId, postOwnerId } = job.data;

  const subscribers = await db.getPostSubscribers(postId);
  const targets = [...new Set([postOwnerId, ...subscribers])].filter(
    (id) => id !== commenterId
  );

  await Promise.all(
    targets.map((userId) =>
      pushService.send(userId, `New comment on post ${postId}`)
    )
  );
}

Report Generation
Reports involve heavy DB queries, aggregations, potentially file generation (PDF/CSV) and upload to S3. This can take minutes. You cannot block an HTTP request for minutes.
js// API: user requests a report
app.post("/reports", async (req, res) => {
  const report = await db.createReport({
    userId: req.user.id,
    status: "pending",
    type: req.body.type,
  });

  await reportQueue.add("generate", { reportId: report.id });

  res.status(202).json({ reportId: report.id, status: "pending" });
});

// Client polls status
app.get("/reports/:id", async (req, res) => {
  const report = await db.getReport(req.params.id);
  res.json({ status: report.status, url: report.downloadUrl });
});

// Worker: does the heavy lifting
async function generateReport(job) {
  const { reportId } = job.data;
  await db.updateReport(reportId, { status: "processing" });

  const data = await db.runHeavyQuery(reportId);
  const pdf = await pdfService.generate(data);
  const url = await s3.upload(pdf);

  await db.updateReport(reportId, { status: "done", downloadUrl: url });
}
The user gets an immediate response. They poll (or get a push notification/email) when the report is ready.

Webhooks
When your system needs to notify external systems of events (payment completed, order shipped), you send HTTP POST requests to their registered URLs. These are outbound webhooks.
You can't send them synchronously — the external server might be slow or down. Enqueue them.
jsasync function dispatchWebhook(job) {
  const { url, payload, secret } = job.data;

  const signature = crypto
    .createHmac("sha256", secret)
    .update(JSON.stringify(payload))
    .digest("hex");

  await axios.post(url, payload, {
    headers: { "X-Signature": signature },
    timeout: 5000,
  });
}
Key points: always sign webhooks so the receiver can verify authenticity. Always retry on failure with exponential backoff. Always log delivery status.
