--------------------------------------------------------------------------
🔸 EXTRA HINGLISH EXPLANATION
--------------------------------------------------------------------------

Dekh bhai, seedha samjh — HTTP me har baar naya connection banta hai. Tu request bhejta hai, server reply deta hai, aur connection turant close ho jaata hai. Agla message bhejna hai? Fir se naya connection banega. Isko bolte hain "stateless, request-response" model — jaise tu ek dukaan pe jaake ek cheez maangta hai, dukaandaar deta hai, aur tu chala jaata hai. Agli baar phir se jaana padega.

WebSocket alag hai. Ek baar connection ban gaya (handshake ho gaya), to wo connection khula rehta hai — jaise ek phone call jisme dono log jab tak chahe baat kar sakte hain, bina baar baar call milaye. Isi wajah se real-time chat, live notifications, multiplayer games — sab WebSocket pe chalte hain, kyunki inme baar baar naya connection banane ka time waste nahi karna padta.

Yaad rakh: 'Open' ek hi baar hota hai, uske baad dono taraf se jitni baar chahe data bhej sakte ho — bina fir se handshake kiye.

🔸 EXTRA HINGLISH EXPLANATION

`clients = []` — ye simplest possible tarika hai connected logo ko yaad rakhne ka. Lekin dhyan de, ye array RAM me hai, disk pe nahi. Matlab agar server crash ho gaya ya restart hua, to ye poora array khatam — saare connections ka record gayab.

Ye theek hai abhi kyunki hum sirf concept samajh rahe hain. Production me is tarah ke naive array ki jagah zyada efficient data structures (Map, Set) use hote hain — jo aage steps me dikhega.

🔸 EXTRA HINGLISH EXPLANATION
--------------------------------------------------------------------------

'Handshake' ka matlab hota hai — browser pehle ek normal HTTP request bhejta hai jisme header hota hai `Upgrade: websocket`. Server agar WebSocket support karta hai to reply karta hai status code `101 Switching Protocols` ke saath. Isliye 'Connection Event' sirf ek hi baar fire hota hai per client — jab tak wo disconnect na ho jaaye.

Pseudocode:

function onMessage(senderSocket, message):
    senderRoom = findRoom(senderSocket)
    for client in clients:
        if client.room == senderRoom:
            client.socket.send(message)

Teen steps — Find, Loop, Match — yehi core logic hai jo har chat app follow karta hai, chahe wo WhatsApp ho ya Discord. Fark sirf itna hai ki unke paas ye lookup O(1) me hota hai (Map ki wajah se), jabki abhi hamara version O(n) hai (loop ki wajah se).

🔸 EXTRA HINGLISH EXPLANATION

JWT (JSON Web Token) ek 'signed' token hota hai jisme user ki info (jaise userId) hoti hai, aur ek signature bhi hota hai jo prove karta hai ki ye token server ne hi issue kiya tha (kisi ne fake nahi banaya). Server jab JWT verify karta hai, to signature check karke confirm karta hai token genuine hai — aur usme se userId nikal leta hai, bina DB call kiye.

Fayda ye hai ki server ko baar baar 'ye user kaun hai' poochne ke liye DB hit nahi karna padta — ek baar verify karo, memory me store kar lo (socket → userId), aur future me wahi use karo.

Ek aur important baat
--------------------------------------------------------------------------

Tum soch rahe hoge:

Agar Room → Socket aur Socket → Room dono same information store kar rahe hain, to duplication kyu?

Bilkul sahi observation.

Ye intentional duplication hai.

Kyun?

Kyuki hume do alag operations fast chahiye:

Chat message: Room se sockets jaldi nikalo → Room → Set<Socket>
Disconnect: Socket se rooms jaldi nikalo → Socket → Set<Room>

Agar sirf ek direction store karte, to doosri direction me hamesha full scan karna padta.

Trade-off:

🟢 Thodi extra memory use hoti hai.
🟢 Bahut fast lookups milte hain.

Production systems me ye trade-off almost hamesha worth hota hai.

--------------------------------------------------------------------------
🔸 EXTRA HINGLISH EXPLANATION
--------------------------------------------------------------------------

Teeno maps ka ek chhota sa 'cheat sheet':

| Map                  | Sawaal jo ye answer karta hai                    |
|----------------------|---------------------------------------------------|
| Socket → User        | 'Ye message kisne bheja?'                          |
| Room → Set<Socket>   | 'Is room me kisko bhejna hai?'                     |
| Socket → Set<Room>   | 'Disconnect hone pe kahan-kahan se hatana hai?'    |

Teeno maps alag-alag sawaal answer karte hain, isliye teeno chahiye — sirf ek se kaam nahi chalega.

Ek chhota sa production tip (aage ke liye, abhi implement nahi karna): jab tera server ek se zyada machine/process pe chalega (horizontal scaling), to ye in-memory maps sirf ek server process ki memory tak limited rahenge. Matlab agar A server-1 se connected hai aur B server-2 se, to server-1 ko pata hi nahi chalega ki B kis room me hai. Isko solve karne ke liye production systems Redis Pub/Sub ya similar external broker use karte hain, jisse saare server instances ek dusre se sync rehte hain. Abhi ke liye single-server version samajhna hi kaafi hai — multi-server wala concept alag learning topic hai.

--------------------------------------------------------------------------
🔸 EXTRA HINGLISH — POORE ARCHITECTURE KA QUICK RECAP
--------------------------------------------------------------------------

Agar tujhe sirf 60 second me poori journey yaad karni ho, to yahi hai:

1. Plain array of sockets → sabko broadcast (galat, sabko sab kuch milta hai)
2. Room field add kiya → sirf same room walon ko bhejna shuru kiya (better, lekin client room bata raha hai bina proof ke)
3. Realize hua client pe trust nahi kar sakte → JWT se authentication add ki (ab pata hai socket kis user ka hai)
4. Room join bhi ab DB se verify hota hai (ab pata hai user sach me us room ka member hai)
5. Teen Maps banaye taaki har operation (send, verify, cleanup) fast rahe:
   - Socket → User (identity)
   - Room → Set<Socket> (broadcast ke liye)
   - Socket → Set<Room> (disconnect cleanup ke liye)

Yehi progression — "pehle simple banao, phir problem dhoondo, phir fix karo" — almost har real-world system design me dikhta hai, chahe wo chat ho, notifications ho, ya kisi aur real-time feature.
